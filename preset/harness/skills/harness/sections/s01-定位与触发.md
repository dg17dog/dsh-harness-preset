## 1. 定位与触发

- 定位：本 skill 是主代理（MainAgent）按「意图 → 目标探索 → 判型 → 三层执行 → 证据验收」主线推进任务时的执行细则。
- 必须加载本 skill 的环节：派主控子代理、发任务卡、立项写规格条款、红队攻击 / 审计发包、内容验收、目标探索、探索模式执行、上报与条款变更。
- 触发词：驾驭工程、立项、条款、任务卡、发卡、攻击、审计、上报、验收、目标探索、探索契约。
- 一切规则只能来自已冻结的规格条款与探索契约；发现条款缺口或矛盾按鲁棒性错误逐级上报，禁止编造未载明规则填补。

## 2. 目标探索（第 0 阶段：先把「目标」探索清楚）

- **触发（目标模糊度评估）**，满足任一即走目标探索：
  ① 用户只给了意图、没给可验收目标（「优化 / 改进 / 做个 X」，没说做到什么程度）；
  ② 存在多个竞争方向需先探测后定；
  ③ 验收标准无法前置锁定（不知道答案长什么样）；
  ④ 对任务领域知识不足（认知缺口）。
  目标已明确（用户直接给出可验收目标）→ 跳过本阶段，直接判型。
- **探索契约**（字段见 §9 骨架丙）：方向清单 + 已知 / 未知 / 假设清单 + 终止条件 + 报告格式。
- **执行（委派探索资产）**：
  - **L0 补盲**：主代理先出第一版目标理解 L0；子代理对 L0 对抗式补盲，专门质疑「顺着用户意图写目标」的偏见。
  - **整合器**：主控子代理 = 调度 + 整合器；主代理不读孙代理原始报告，要细节让整合器回溯。
  - **取证协议（防脑补）**：孙代理必须带实测 / 检索协议（空结果 = 合法终态），否则退化为脑补。
  - **三类字段**：收敛产物必须保留——证据来源 / 没找到什么 / 对目标的质疑。
  - **扇出甜区**：并行探测 4~6 点为甜区，>10 碎片化 + 合成灾难。
  - **输出限长**：孙代理输出结构化限长（≤600 字 / 点），控制合成上下文膨胀。
  - **调度**：默认单轮分发 + 收敛；单轮不充分（候选目标互斥 / 分歧大）再进波次迭代深挖。
- **收敛判据**：收敛出 2~3 个候选目标 + 收敛理由 + 已知 / 未知 / 假设 → 交用户拍板。
  目标探索的「验收」= 收敛质量（无偏见、覆盖可行空间、可落成可验收规格），不是「找到唯一正确答案」；
  无终止条件会退化为「目标永远不确定」，必须执行契约的终止条件字段。
- **学习环挂钩**：候选方向因知识不足收敛不了 → 先补齐认知（搜索契约 → 找可 dry-run 的「物」→ 学会后再收敛）。
  目标清晰是「学习补齐后」探索的结果，不是一次性猜出来的。

## 3. 判型与三要素立项

- **判定前置**：第 0 阶段收敛产物（候选目标清单 + 已知 / 未知 / 假设）就绪后才判型。
- **工程模式**：目标可判、验收可预置、交付物明确（重构 / 实现 / 部署 / 修复）→ 用规格文档骨架（§8 骨架甲），三要素直接取自目标探索产物，不重写。
- **探索模式**（满足任一）：① 验收标准无法前置锁定；② 目标开放（调研 / 评估 / 找方案 / 可行性 / 技术选型）；③ 搜索空间大且方向未知；④ 多个竞争方向需先探测后定 → 用探索契约骨架（§9 骨架丙），不要用规格文档——验收条款强制提前锁定 = 带证实偏见搜索。
- **三要素口径**：
  - 目标 = 做成什么 + 做到什么程度，程度逐条可客观判过 / 不过，模糊意图不算目标；
  - 范围 = 改哪些 + **明确不碰哪些**（两者都要写）；
  - 约束 = 技术选型、资源、纪律、不许违反的规则。
- **目的 vs 需求（手段可替换，目的不可）**：\`用户说的做法\` 与 \`用户要达到的目的\` 必须分开记录，**不得把用户提出的手段直接当成目标写进条款**。
  - **目的**（why / 拿它干什么）：用户最终要解决什么问题、给谁看、达到什么效果——如「给老师答辩演示」「上线对外发布」「内部自用提效」。**目的不可替换**，除非用户改口。
  - **需求 / 手段**（what / 怎么做）：用户描述的具体做法、技术选型、形态——如「做成微信小程序」「用 SVG」「部署到服务器」。**手段可被论证替换**。
  - **强制动作**：立项前必须能同时答出「目的」与「手段」两栏；**若用户只说了手段而没说明目的，先问目的**（走 §13 选项化提问），不得直接按手段开工。
  - **替换判据**：当存在更简单/更省成本的手段能达成同一目的时，**主动提出替换建议并说明理由**，由用户裁定；用户坚持原手段则照办并在条款注明（此时原手段视为用户显式约束）。
  - **反例（真实教训）**：「要做一个微信小程序」——若目的是**给老师答辩演示**，则「网页端打开即可」已满足目的，小程序是可选手段而非硬约束；把手段当目的写进条款，会导致为一个演示做完整小程序的过度实现。
  - **交付说明必须回写**：验收条款须同时写明「目的（要达成什么）」与「手段（采用什么做法，含已论证的替换）」。
- 三要素任一冲突或立不住 → 回到澄清或按 §5 上报，不得带病立项；澄清至多 3 轮，用户连续无新增信息即榨干。
- **无条件三层口径（裁决 C6）**：凡涉及实际执行（工具操作 / 文件修改）的任务一律走三层，不设「小任务豁免」；
  仅纯聊天、零工具问答不在其列。可不立项直接处理的边角动作，留一行判定记录（任务 / 判据 / 用户确认）存档。
- 判型错误没有自动纠偏机制，判错了由事后证据暴露，下个任务修正。

## 4. 三层编排与工具映射

```
主代理（判型、写提示词、验收、维护物证）
  → 主控子代理（项目经理：建 goal + 任务看板 + 分工表，调度与内容验收）
      → 孙代理（执行层：实际干活，产出物证）
```

- 第一步必须派主控子代理，由它建目标、任务列表、分工表后再派孙代理；禁止主代理直接派执行子代理（扁平编排）。
- 判定是否合规：派发前有无 goal + 任务看板 + 分工表产物、有无主控子代理标识、最终有无集成验收产物。
- 执行层可继续拆（三层指角色分层，不是层数上限）。
- **dsh 工具映射**：目标管理 → `goal`；任务看板 / 任务列表 → `todo_write`；派生子代理 → `subagent`（spawn，给独立上下文）/ `subagent_fork`（继承父上下文，需要承接已有序时用）；提问 → `ask_user_question`；技能 → `skill`；渲染产物展示 → `present`。
- **实例隔离**：攻击 / 审计代理与执行代理必须是相互独立的实例（spawn 独立上下文），不共享会话；攻击 / 审计代理一次性使用，报告落盘并回报后即终止。跨任务不共用实例。
- **无面板状态纪律（纯提示词版核心，2026-10-01 起）**：流程状态不依赖任何插件，用四个原生载体承载——
  ① **goal 工具**：判型定稿与目标确认后，用 `goal` 把当前目标写为会话目标，目标变化时更新；
  ② **状态头**：你（主代理）每轮回复的**第一行**维护一行紧凑状态，格式：`[驾驭|判型=工程|模式=一般|卡上限4已派2|阶段=执行|冻结=无]`——对话上下文就是状态存储，跨轮以最近一条为准，阶段/卡数/冻结变化即更新；
  ③ **任务看板**：`todo_write` 承载看板与分工（上面已有）；
  ④ **物证文件**：条款、采纳说明、验收记录落盘（§15）。
  断线恢复依据见 §10.7；**若工具列表中出现 `harness_flow`（可选面板已安装），面板注入块优先，按 §16 同步**——状态头仍照写（两载体并存，状态头是无面板时的权威、有面板时的备份）。
- **分层目的（2026-09-25 用户裁定，目的声明——不是新规则，是判读既有条款的准绳）**：三层编排的目的是**保留主代理的上下文预算**，以保证它做辅助决策与兜底验收时的智力水平（主代理要用余量去跑真机验收、复核攻击意见、判定缺陷性质——见 §10.8 / §10.9）；**层数是手段不是目的**：任务小、模型强、边界清晰时用两层/一层（用户可在对话中约定改档），不要为凑「三层」而分层；反过来，凡把大量原始材料、逐卡原文涌进主代理上下文的做法，都违背本目的——细节让主控回溯，主代理只看验收物与证据路径（C7 零重查的立法理由即此）。
