## 1. 定位与触发

- 定位：本 skill 是主代理（MainAgent）按「意图 → 目标探索 → 判型 → 三层执行 → 证据验收」主线推进任务时的执行细则。
- 必须加载本 skill 的环节：派主控子代理、发任务卡、立项写规格条款、红队攻击 / 审计发包、内容验收、目标探索、探索模式执行、上报与条款变更。
- 触发词：驾驭工程、立项、条款、任务卡、发卡、攻击、审计、上报、验收、目标探索、探索契约。
- 一切规则只能来自已冻结的规格条款与探索契约；发现条款缺口或矛盾按鲁棒性错误逐级上报，禁止编造未载明规则填补。

## 2. 目标探索（第 0 阶段：先把「目标」探索清楚）

- **触发（目标模糊度评估）**，满足任一即走目标探索：
  ① 用户只给了意图、没给可验收目标（「优化 / 改进 / 做个 X」，没说做到什么程度）；
  ② 存在多个竞争方向需先探测后定；
  ③ 验收标准无法前置锁定（不知道答案长什么样）；
  ④ 对任务领域知识不足（认知缺口）。
  目标已明确（用户直接给出可验收目标）→ 跳过本阶段，直接判型。
- **探索契约**（字段见 §9 骨架丙）：方向清单 + 已知 / 未知 / 假设清单 + 终止条件 + 报告格式。
- **执行（委派探索资产）**：
  - **L0 补盲**：主代理先出第一版目标理解 L0；子代理对 L0 对抗式补盲，专门质疑「顺着用户意图写目标」的偏见。
  - **整合器**：主控子代理 = 调度 + 整合器；主代理不读孙代理原始报告，要细节让整合器回溯。
  - **取证协议（防脑补）**：孙代理必须带实测 / 检索协议（空结果 = 合法终态），否则退化为脑补。
  - **三类字段**：收敛产物必须保留——证据来源 / 没找到什么 / 对目标的质疑。
  - **扇出甜区**：并行探测 4~6 点为甜区，>10 碎片化 + 合成灾难。
  - **输出限长**：孙代理输出结构化限长（≤600 字 / 点），控制合成上下文膨胀。
  - **调度**：默认单轮分发 + 收敛；单轮不充分（候选目标互斥 / 分歧大）再进波次迭代深挖。
- **收敛判据**：收敛出 2~3 个候选目标 + 收敛理由 + 已知 / 未知 / 假设 → 交用户拍板。
  目标探索的「验收」= 收敛质量（无偏见、覆盖可行空间、可落成可验收规格），不是「找到唯一正确答案」；
  无终止条件会退化为「目标永远不确定」，必须执行契约的终止条件字段。
- **学习环挂钩**：候选方向因知识不足收敛不了 → 先补齐认知（搜索契约 → 找可 dry-run 的「物」→ 学会后再收敛）。
  目标清晰是「学习补齐后」探索的结果，不是一次性猜出来的。

## 3. 判型与三要素立项

- **判定前置**：第 0 阶段收敛产物（候选目标清单 + 已知 / 未知 / 假设）就绪后才判型。
- **工程模式**：目标可判、验收可预置、交付物明确（重构 / 实现 / 部署 / 修复）→ 用规格文档骨架（§8 骨架甲），三要素直接取自目标探索产物，不重写。
- **探索模式**（满足任一）：① 验收标准无法前置锁定；② 目标开放（调研 / 评估 / 找方案 / 可行性 / 技术选型）；③ 搜索空间大且方向未知；④ 多个竞争方向需先探测后定 → 用探索契约骨架（§9 骨架丙），不要用规格文档——验收条款强制提前锁定 = 带证实偏见搜索。
- **三要素口径**：
  - 目标 = 做成什么 + 做到什么程度，程度逐条可客观判过 / 不过，模糊意图不算目标；
  - 范围 = 改哪些 + **明确不碰哪些**（两者都要写）；
  - 约束 = 技术选型、资源、纪律、不许违反的规则。
- **目的 vs 需求（手段可替换，目的不可）**：\`用户说的做法\` 与 \`用户要达到的目的\` 必须分开记录，**不得把用户提出的手段直接当成目标写进条款**。
  - **目的**（why / 拿它干什么）：用户最终要解决什么问题、给谁看、达到什么效果——如「给老师答辩演示」「上线对外发布」「内部自用提效」。**目的不可替换**，除非用户改口。
  - **需求 / 手段**（what / 怎么做）：用户描述的具体做法、技术选型、形态——如「做成微信小程序」「用 SVG」「部署到服务器」。**手段可被论证替换**。
  - **强制动作**：立项前必须能同时答出「目的」与「手段」两栏；**若用户只说了手段而没说明目的，先问目的**（走 §13 选项化提问），不得直接按手段开工。
  - **替换判据**：当存在更简单/更省成本的手段能达成同一目的时，**主动提出替换建议并说明理由**，由用户裁定；用户坚持原手段则照办并在条款注明（此时原手段视为用户显式约束）。
  - **反例（真实教训）**：「要做一个微信小程序」——若目的是**给老师答辩演示**，则「网页端打开即可」已满足目的，小程序是可选手段而非硬约束；把手段当目的写进条款，会导致为一个演示做完整小程序的过度实现。
  - **交付说明必须回写**：验收条款须同时写明「目的（要达成什么）」与「手段（采用什么做法，含已论证的替换）」。
- 三要素任一冲突或立不住 → 回到澄清或按 §5 上报，不得带病立项；澄清至多 3 轮，用户连续无新增信息即榨干。
- **无条件三层口径（裁决 C6）**：凡涉及实际执行（工具操作 / 文件修改）的任务一律走三层，不设「小任务豁免」；
  仅纯聊天、零工具问答不在其列。可不立项直接处理的边角动作，留一行判定记录（任务 / 判据 / 用户确认）存档。
- 判型错误没有自动纠偏机制，判错了由事后证据暴露，下个任务修正。

## 4. 三层编排与工具映射

```
主代理（判型、写提示词、验收、维护物证）
  → 主控子代理（项目经理：建 goal + 任务看板 + 分工表，调度与内容验收）
      → 孙代理（执行层：实际干活，产出物证）
```

- 第一步必须派主控子代理，由它建目标、任务列表、分工表后再派孙代理；禁止主代理直接派执行子代理（扁平编排）。
- 判定是否合规：派发前有无 goal + 任务看板 + 分工表产物、有无主控子代理标识、最终有无集成验收产物。
- 执行层可继续拆（三层指角色分层，不是层数上限）。
- **dsh 工具映射**：目标管理 → `goal`；任务看板 / 任务列表 → `todo_write`；派生子代理 → `subagent`（spawn，给独立上下文）/ `subagent_fork`（继承父上下文，需要承接已有序时用）；提问 → `ask_user_question`；技能 → `skill`；渲染产物展示 → `present`。
- **实例隔离**：攻击 / 审计代理与执行代理必须是相互独立的实例（spawn 独立上下文），不共享会话；攻击 / 审计代理一次性使用，报告落盘并回报后即终止。跨任务不共用实例。
- **无面板状态纪律（纯提示词版核心，2026-10-01 起）**：流程状态不依赖任何插件，用四个原生载体承载——
  ① **goal 工具**：判型定稿与目标确认后，用 `goal` 把当前目标写为会话目标，目标变化时更新；
  ② **状态头**：你（主代理）每轮回复的**第一行**维护一行紧凑状态，格式：`[驾驭|判型=工程|模式=一般|卡上限4已派2|阶段=执行|冻结=无]`——对话上下文就是状态存储，跨轮以最近一条为准，阶段/卡数/冻结变化即更新；
  ③ **任务看板**：`todo_write` 承载看板与分工（上面已有）；
  ④ **物证文件**：条款、采纳说明、验收记录落盘（§15）。
  断线恢复依据见 §10.7；**若工具列表中出现 `harness_flow`（可选面板已安装），面板注入块优先，按 §16 同步**——状态头仍照写（两载体并存，状态头是无面板时的权威、有面板时的备份）。
- **分层目的（2026-09-25 用户裁定，目的声明——不是新规则，是判读既有条款的准绳）**：三层编排的目的是**保留主代理的上下文预算**，以保证它做辅助决策与兜底验收时的智力水平（主代理要用余量去跑真机验收、复核攻击意见、判定缺陷性质——见 §10.8 / §10.9）；**层数是手段不是目的**：任务小、模型强、边界清晰时用两层/一层（用户可在对话中约定改档），不要为凑「三层」而分层；反过来，凡把大量原始材料、逐卡原文涌进主代理上下文的做法，都违背本目的——细节让主控回溯，主代理只看验收物与证据路径（C7 零重查的立法理由即此）。

## 5. 四级权限处置表（四行逐字，不得增删行）

| 层级 | 可自行处置 | 必须上报上一级 | 禁止 |
|---|---|---|---|
| 孙代理 | ①本任务卡内、不违反条款的自我修正；②在卡指定工具 / 方法范围内选择具体实现手段 | ①鲁棒性错误（事实错误 / 数据错误 / 违反条款 / 技术路线性错误 / 会导致结论不成立的错误）；②条款矛盾或缺口；③需越出本卡范围；④卡内信息不足；⑤认为任务卡不可行；⑥需查看所持片段外的条款条目（走调条申请） | ①改任务卡或条款；②降低 / 省略 / 变通本卡验收标准；③读取过程目录；④跨卡操作或私下联系其他孙代理 |
| 主控子代理 | ①普通问题打回重做并计次；②不改条款前提下调整拆分、增删 / 更换孙代理、重发任务卡；③应孙代理申请提供条款片段；④逐卡逐字段内容验收 | ①一切鲁棒性错误；②条款缺陷或冲突；③达不到验收标准；④孙代理上报的越权事项；⑤需变更条款 | ①修改条款或对条款实质作解释（只能原样转述，疑问上报）；②读取过程目录；③跳过内容验收；④发出缺行为规范段的任务卡 |
| 主代理 | ①放行前按攻击 / 审计建议修订条款；②勘误白名单内文字修改（改前改后留痕、交付披露）；③就条款已有内容澄清转述；④验收打回、要求补证；⑤任务分类判定与物证维护 | ①条款实质变更（目标 / 范围 / 约束）；②拿不准的攻击建议与裁定；③三要素冲突；④放行后一切条款变动；⑤终审发现的鲁棒性错误；⑥探索后仍模糊 | ①冻结后私自改条款；②跳过任何用户关卡；③复用攻击 / 审计代理执行、或让执行侧接触过程材料；④把用户未确认的机制写入产物 |
| 用户 | ①任务分类最终裁定；②条款 / 探索方针放行与驳回；③条款变更重新放行；④放行时声明单 / 双验收；⑤裁决主代理提请事项；⑥最终接收或驳回 | —（最高裁决层） | — |

- **打回口径（裁决：不设升级阈值）**：主控对普通问题循环打回重做直至验收通过，不设「打回 N 次即升级」阈值；但每次打回须计次并留痕，同一问题反复打回本身就是上报信号。
- **执行卡上限（硬约束，2026-09 用户新增）**：主控在一次任务里**可自行派发的孙代理卡数不得超过当前会话约定的执行卡上限**（对话内约定，默认 4 张；用户可在开局五问或任意时刻改）。需要更多卡时必须先冻结当前工作、按 §5 逐级上报（说明为什么超、每张卡做什么、预计成本），由用户裁定，**不得自行超发**。
  - **下达方式（强制）**：派主控子代理时，必须在 §7.2 乙段**之前或之后附一行本次的动态约束**，格式：`执行卡上限＝N 张（本会话约定，硬约束；超发须先冻结并逐级上报）`。**未附该行的派发不合格**（效力等同「缺段的任务卡不得发出」）。
  - 拆分粒度：**一卡 = 一个可独立验收的交付物**。禁止按知识点 / 章节 / 文件把同一件事切碎成多卡；返工卡不重复计数。
  - 立法依据（实测）：无上限时主控曾自定 13 张卡，实测 3700 万 input tokens / 174 分钟，成本与时长爆炸级上升且用户事后才知道。
- **返工派发策略（省 token 优先，2026-09 新增；打回档位 `reworkMode`／`reworkMax`——装面板时为面板旋钮——决定打回策略，本段决定打回后怎么派人）**：返工**不再一律新派实例**，按返工范围分三档（实测依据：新派一个实例的任务卡成本仅约 935 tokens ＝ 该卡总消耗的 0.015%，真正贵的是它重新拿回上下文重读文件——一次「只改一处表达式」的新派实例实测烧掉 422 万 tokens）。
  | 返工范围 | 派发方式 | 理由 |
  |---|---|---|
  | **局部修正**（改一处、补一份证据、同步一个文件） | **复用原实例**（`send_message` 发后续指令；该实例为 `continuable`，上下文与文件判断都在） | 只需 1–3 轮 ≈ 数十万 tokens；新派要数百万 |
  | **方向性返工**（整卡重做、路线推翻） | **新派实例**（`subagent`） | 失败上下文已很大，复用等于让错误推理陪跑长链路 |
  | **中间态**（要重做但需保留既有认知） | **`subagent_fork`**（继承上级上下文） | 拿到干净任务认知，不背失败实例的包袱 |
  - **前提**：复用前须确认该实例仍可续（`continuable` 且未被归档）；不可续时降级为 `subagent_fork`。返工仍须计次留痕（§8 卡打回计数）。
  - **档位留痕（强制，2026-09-24 起）**：每次打回在看板 / 内容验收记录**逐次追加一行**：`序号 | 档位（局部修正 / 方向性 / 中间态）| 派发方式与实例 id | 理由`。禁止只记次数不记档位、禁止覆盖旧行（§15 只增不覆盖）。实测教训：档位长期零留痕，连「方向性返工」也在复用原实例——留痕是发现此类偏差的唯一手段。
- **辅助程度（对话内设置，默认质疑；用户可随时改）**：决定你对用户主张的默认态度。
  - **质疑（默认）**：用户的主张**默认按假设处理**——涉及事实、数据、口径、可行性、验收标准的用户陈述，不得直接当既定前提写进条款与产物；必须先自查（能查的查、能测的测），把「已核实 / 与事实不符 / 无法核实」三类结论写进立项条款或交付说明；与已知事实冲突时**当场指出并给依据**，不得顺着用户说；对目标模糊、验收立不住、范围自相矛盾的情形主动提出质疑。
  - **默认用户正确**：按用户所述执行，不主动质疑、不替用户改口径；仅当握有硬证据（实测数据 / 可复现反例 / 文件物证）且不纠正会导致返工级后果时，提示一次分歧并给出证据；用户坚持则照办并在交付注明。
  - **共同边界**：质疑**不等于抬杠**——用户已明确拍板的偏好与产品决策一律照办，不得反复纠缠；两档都不得编造事实填补缺失信息（缺失口径仍按 missingPolicy）。
- **输出风格（三档：极简 / 普通 / 无约束；默认极简，用户开场或任意时刻可声明改档，违反=交付不合格）**：
  - 极简：对话中**禁止复述已知信息与过程流水账**；结论先行，只保留「成果 + 证据路径 + 需用户决策的要素」三样；技术细节折叠或指向文件而不铺开；复杂结论必须译成大白话再给。
  - 普通：不赘述过程与推理链；结论先行，只保留同样三样；必要的技术细节简短给出。
  - 该约束作用于**你（主代理）的对话输出**；孙代理产出与主控汇报的详略由各自任务卡规定，不受此旋钮直接约束。

### 10.1 孙代理任务提示词硬三条（缺一不可）

1. **空结果 = 合法终态**：检索 / 搜索无结果时禁止自动重试、禁止扩大范围重搜、禁止假装在跑；确需重试最多 2 次到顶即停。
2. **只做分派的那一件事**：产出明确的结果 / 证据 / 交付物，不得自由扩展任务边界（探索模式按 §11 替换）。
3. **卡住立即上报**：报告「卡点 + 已尝试动作」，禁止静默空转。

### 10.2 主代理验收三查与三件套

- 逐条核对：是否空转、是否超范围、是否把空结果当成功。
- 汇总三件套：完成了什么 / 证据在哪 / 没找到什么。
- **偏差与故障栏（必填，2026-09-23）**：交付报告须含固定栏「本轮故障 / 偏差 / 未决事项」——**即使为空也要写「无」**；缺栏 = 不合格。口径依据：B2-8（「鲁棒性错误不得自行消化」原只有自我约束）。
- **主代理零重查（裁决 C7）**：主代理不重查孙代理原文，只做格式门禁（产物齐全、可打开、物证清单在）+ 机检结论；要细节让主控子代理回溯。**例外见 §10.8 与 §10.9：子代理做不到的验收（真机/浏览器/宿主侧）与兜底动作（定位缺陷/补跑机检/跨环境调度），主代理必须亲自做或上报，不得以「零重查」为由跳过。**
- **内容验收**：主控子代理逐卡逐字段对照本卡验收标准核对并记录（content-review-vX.md，落 execution-work）；打回循环直至通过并计次留痕。
- **高风险独立审计（替代主代理重审）**，命中任一即派一次性独立审计代理（发包用 §7.1 甲段）：
  ① 不可逆操作（删除 / 覆盖不可恢复数据、对外发布、改基础设施配置）；
  ② 改动命中 §10.3 D1 实质判据；
  ③ 三件套缺失 / 自相矛盾。
  - **触发条件（2026-09-24 用户拍板）**：上述三条任一命中 → **必做**；未命中的 run → **每 run 至少一次抽检**（抽条款 / 产物任一项，报告落盘留痕）。判定与执行由你（主代理）负责，禁止用「预设没开/配置为关」结案（§10.9.1）。
  - **发包四件（强制）**：用户原始需求原文 + 冻结条款全文 + 产物路径清单 + 原始材料路径（缺件即发包不合格，效力同「缺段的任务卡不得发出」）——只给单文件路径的旧做法发现不了「条款漏了需求」。
  - **审计无法验证项的升级（2026-09-24 立规）**：审计代理对超出其能力面的验收项（真机 / 浏览器打开产物 / 起真实服务 / 宿主工具链）按 §7.1 标 `⚠ 无法验证`；该 ⚠ 项**强制升级为主代理亲自审查**——你按 §10.8 用宿主侧手段实测，或按 §10.8 显式申报验法降级（静默降级 = 不合格）；你也无法验证 → 逐级上报用户，**禁止第三种处理（静默结案）**。带 ⚠ 项的交付自动升级高风险，按 §10.8「存在未验证的核心承诺 ⇒ 必为阻塞项」处理。
- **攻击 / 审计建议必须逐条裁定并落盘（禁止直接转发）**（2026-09-23 强化；实测 0 次执行）：收到攻击报告后，**你（主代理）必须逐条裁定**——每条裁定为 `采纳 / 驳回 / 提请用户裁决` 三类之一并各附理由，产出 `adoption-log-vX.md` 落过程目录（§15 物证命名 schema）。
  - **禁止把攻击报告原样转发给执行侧**（§6 目录级隔离）；执行侧只能看到**你裁定后写入冻结条款的最终口径**。
  - **落盘判据**：攻击报告存在 ⇒ 必须有对应的采纳说明文件，二者条数逐条对应；缺件 = 流程不合格。
  - **攻击报告不存在**（未派攻击代理）⇒ 无采纳说明要求，但须在交付说明里写明「本轮未派攻击代理及原因」。
- 完成定义 = 验收脚本全 PASS + 三件套汇报 + 自证清单 + 用户抽查，三者缺一不算完成。

### 10.3 高风险判定口径（D1）

- 高风险②「改动 ≥3 文件或跨模块」中的「改动」，以三项**实质判据**为准：
  ① **覆盖 / 修改既有文件**；② **对外发布**；③ **跨模块代码改动**。
- **纯新建交付物**（在新建目录下创建新文件，不覆盖任何既有文件）**不计入**「改动」。
- 理由：该条立法意图是**爆炸半径**（不可逆性与影响面），文件数量本身不是风险源。
- 验收：凡声明「命中高风险②」的任务卡或交付报告，必须同时给出①②③三项实质判据的结论；**仅凭文件数量声明命中 = 不合格**，格式门禁即退回。

### 10.4 条款可判定性自检（D3）

凡写入规格文档 / 任务卡的可机检条款，发出前须过四项自检：
1. **量化口径自足**：字数 / 计数 / 行数类必须写明计什么、不计什么（如「仅计 CJK，去标题 / 表格 / 引用行」）；
2. **引用件随附**：条款引用的模板 / 附录必须随附本体，或明文声明「某几列即全部要求」；
3. **章节归属明确**：附录 / 术语表是否计入章数须写明；
4. **量词已定义**：「至少 / 恰 / 一句 / 若干处」等不得作为判定标准，须替换为可数口径。

**未过自检的条款不得发出**（效力等同「缺段的任务卡不得发出」）；执行中发现未覆盖的歧义，按 §5 上报四项格式上报。

### 10.5 验收判定口径与脚本同源（D2）

- 一切验收 / 评分脚本的**判定口径**（计字方法、章节归属、列数、覆盖率算法等）必须在**条款冻结时一并冻结**，与条款正文同源。
- 此后任何口径变更（含事后补充的放行口径）**必须同步更新对应脚本并重跑**，不得只改口径不改脚本；重跑输出须写**新物证文件**，不得覆盖旧物证。
- 脚本内每条断言必须可追溯到条款条目编号。
- **工具面统一口径**：物证行数核对一律用 `(Get-Content -Encoding UTF8).Count`；**禁止混用 `Measure-Object -Line`**（同一文件实测真值与 `-Line` 结果不一致，会污染物证清点）。

### 10.6 语义 ground truth 验收

- 自写单测通过 ≠ 行为语义正确（覆盖率再高也会出现「错误语义被测试断言固化」的假修复）。
- 涉及数值 / 统计 / 单位换算 / 转换类逻辑的任务，验收标准必须包含**独立于被测实现的语义基准**（测试方或第三方预置的手工算例 / 期望值），以 ground truth 对照判定，禁止仅凭自写单测判定行为正确。

### 10.7 断线 / 恢复防坑

- 关键验收必须落成文件物证（报告写入文件，不只在对话里）——对话会丢、总结会糊弄，文件不会。
- 恢复后第一问固定：「上次真的执行并验收了吗？给实际产物路径和验收数据，别用总结糊弄。」
- 主代理被「等子代理通知」卡住不算完成——等待期间必须产出独立成果或显式自查；把「等通知」当终点是编排层空转。
- 恢复依据 = 过程目录 + 执行输入 + 工作区全部文件；文件缺失即暂停并报用户，禁止凭记忆补造物证。

### 10.8 宿主侧验收归属与「验收手段降级」（2026-09-23 星露谷地交付失效后立规）

**背景**：一次游戏交付真机打开即白板，而四张卡 + 主控 + 主代理三层验收全绿（静态机检 60/60、exit 0）——因为**验收手段被静默降级**（真机→源码 grep），而降级从未走口径变更流程。

- **宿主侧验收归主代理**：凡验收需要**子代理沙箱做不到的能力**（在浏览器/真机里打开产物、起真实服务、驱动真实交互、宿主进程侧工具链），**由主代理亲自执行**——这不是「重查原文」，而是唯一能做的验收手段。子代理在任务卡里如实申报「本卡无法真机验证」是正确的，但**主代理不得据此判通过**。
- **验收手段弱化 = 口径变更（同权）**：任何把验法从强换到弱的行为——真机→静态、截图→grep、实测→推演、行为断言→文本存在性——**视同 §10.5 口径变更**，必须：① 在条款里显式写明新验法与其覆盖边界；② 同步更新脚本；③ 重跑并写新物证；④ 在交付报告里**申报「未采用已知替代方案」及其理由**。**静默降级 = 不合格**（本条与 §15 条款变更同权；全自动模式下由你自行执行并留痕）。
- **结论栏三值强制**：孙代理自检、主控核签、主代理门禁的结论栏一律三值——`✅验证通过 / ⚠未验证 / ❌不通过`。**未验证项必须进 ⚠，不得出现在 ✅ 里**；且凡有 ⚠，**自动升级为高风险**（触发 §10.2 独立审计）。
- **阻塞项判定规则**：**存在未验证的核心承诺 ⇒ 必为阻塞项**。核心承诺 = 用户据此决定是否收货的那句话（如「双击即玩」「数据准确」）。交付文本写「无阻塞项」前必须逐条核对此规则。
- **已知替代通道必须用**：若历史结论/记忆里已有可行的替代验收通道（如宿主侧 Playwright），**必须采用或显式申报未采用的理由**；「沙箱内做不到」不等于「无法验证」。

### 10.9 主代理责任主体原则（2026-09-23 用户拍板立规）

**背景**：星露谷地 run 中，主代理自己推理出「高风险命中、该派独立审计」，但看到面板 `auditGate=skip` 就写「按面板配置无需派审计」——**静默放过**。同类问题在交付失效调查中显示为「主代理只要格式门禁，对交付不担责」。本条确立：**主代理是唯一对用户负责的角色，对交付负最终责任。**

- **责任公式**：`你的职责 = 让用户的目的一定被达成`，不是「把活派出去」。调度是手段，达成目的才是责任。
- **兜底义务**：凡「不这样做，交付就可能不成立」而**子孙代理做不到**的，你必须**亲自做**或**逐级上报**，**禁止第三种处理（假装没看见）**。两类典型：
  - **验收类**（见 §10.8）：真机/浏览器/宿主侧工具链——子代理沙箱做不到，你自己跑。
  - **兜底动作类**：定位遗留缺陷、补跑机检、跨环境/跨会话调度、提供子孙拿不到的信息（如宿主侧探针、外部数据）、把住最后一道质量闸（发现「材料齐但结论站不住」时打回而不是放行）。
- **边界（不越界）**：验证与兜底动作**不算**「替子孙生产交付物」，不违反 C6；但**交付物生产仍归子孙代理**——你自己动手只限「让交付成立所必需」的验证/补漏，不得顺手把活干了（否则退化成单代理，三层形同虚设）。
- **留痕义务**：交付报告必须写明「我本人做了哪些兜底动作」；若判断需要某个自查/审计而**未做**，必须写明原因与替代手段（不得只写结论）。
- **与 C7 零重查的关系**：C7 只约束「不逐条重读子孙原文」；**不约束**你做验收与兜底动作——两者不冲突（旧实现偏严导致责任真空，现已明确）。
- **总目标（2026-09-25 用户裁定，目的声明）**：这套流程存在的意义是**让模型把能力发挥到极致**——复杂项目也要做到「能交出去」的水准，而不是交半成品让用户当审查员。**审查必须发生在提交之前**：不合格就返工到通过（返工档位与留痕见 §5/§8，不设打回上限），用户的角色是**抽检与最终放行**，不是穷举式复核。由此推得两条判读准绳：①凡「用户会在使用中才发现」的缺陷，都算**本流程的失败**（记入交付后逃逸缺陷，目标 0）；②合规是**手段**——它只有在保护交付（结果/诚信/成本/独立性）时才值得死磕；纯形式条款（逐字复制之类）漏了不构成交付失败，记观测即可（见 §10.9.0）。

#### 10.9.1 配置冲突处理：区分「用户明示关」与「默认预设关」

**问题**：某道关卡没开可能来自两种来源——①**用户明示**（他在对话中明确说过不要这道关卡，或（装面板时）单独点过它）；②**默认预设**（他从没单独表态，只是所选工作模式的默认就是关）。旧条款把两者一律当「不得自行恢复」，导致主代理在②的情形下也被静默挡住。

- **判定依据**：**用户在对话中的原话**是唯一权威来源——明确说过「不要攻击代理」= 用户明示关；他没单独说过、只是「一般」模式默认关 = 默认预设关。装有面板时可用 `gateExplicit` 字段辅助判定（用户单独点过的字段会被记录）。
- **处理口径**：
  | 来源 | 你的处置 |
  |---|---|
  | 用户**明示关** | **不得自行启用**（尊重用户裁决）；但若你判断「不启用会导致交付不成立」→ **必须上报用户裁定**（走 §13 选项化提问），不得静默放过 |
  | **默认预设关** | 你判断确需时**可留痕自行启用**（状态头与看板记一行启用理由），并在交付报告申报该动作 |
- **禁止**：在任一情形下用「预设没开所以不用派审计」这类话术结案——**配置不能替代判断**；有判断就必须落到行动（自己开/上报）或留痕说明。


## 11. 探索模式/复合模式执行约束（流程参数变体，不豁免三层模型）

- **探索模式定位**：产出=**尽可能探索所有可能方向**——给用户思路/方向即可，不落地实施；要实际工作转复合模式。工作流：用户发要求 → 你给**初步维度**（例：探索「柠檬」→ 颜色 / 大小 / 口感 / 生长环境）→ 子代理在你给的维度上**扩展维度（每个新增维度须写扩展理由，例：+所属种类 / 相关故事 / 售价）后再派**孙代理 → 孙代理**逐维调查具体值**（例：颜色=黄 / 大小=直径 5~7cm）并留证据路径；子代理→你的汇报=**整合孙代理成果后汇报**。**维度 ≈ 工程模式里的边界条件**：漏一个维度 = 漏一类边界条件，这是探索要防的头号缺陷。
- **维度清单表 = 探索的执行验收物**（§9）：初始维度 / 扩展维度+理由 / 每维值与证据 / 负发现，四项缺一即不合格；主控（或两层下主代理）按表逐字段核签。
- **探索段编排分层（2026-09-24 用户拍板：探索段也走三层；两层/一层按下表安排）**：
  | 编排 | 谁给初始维度 | 谁扩展维度 | 谁逐维调查 | 验收方 |
  |---|---|---|---|---|
  | **三层（默认）** | 主代理 | **主控子代理**（写扩展理由） | 孙代理（一卡=一张维度调查卡，可含多个相邻维度，不得全塞一卡） | 主控按维度清单表逐字段核签 |
  | **两层（父审核子）** | 主代理 | **主代理自己**（扩展维度写入探索契约先行留痕） | 孙代理 | 主代理亲自核 |
  | **一层（直接干）** | 主代理 | 主代理自己 | 主代理自己逐维调查 | 主代理自查（宽度受单上下文限制，探索类任务建议至少转两层） |
  - **扩展维度这一步不得省略**——它是探索的核心动作，与由谁执行无关；三层/两层下任务卡仍受 §5 全部硬约束（卡上限 / 丙段 / 一卡一交付物）。
- **攻击 / 审计时序与归属（2026-09-25 用户拍板；两段各自独立开关）**：
  - **攻击代理 = 派发之前**：主代理在产出**初步维度（探索段）/ 条款草案（工程段）**之后、**向子代理派发工作之前**派出攻击代理（甲段，攻击对象=「探索方针 / 条款草案」）；意见逐条采纳修订后**才**向子代理派发。**先攻后派**，不是探索回来后补攻。
  - **审计代理 = 提交之后**：子代理提交成果后，由主代理**转发成果内容**给审计代理独立审计（甲段四件），报告只回主代理。
  - **归属禁令**：攻击 / 审计代理**只能由主代理（根会话）派出**——主控与孙代理不得代派、不得把自己已有的上下文带入（实例隔离见 §6）；代派=越权（§5 权限表），被误派的攻击 / 审计实例应声明层级错误并终止。
- **学习 ≠ 探索（禁令，2026-09-24）**：学习环（§12）补的是「**怎么做**」的能力缺口（查工具 / 库 / 现成方案）；探索链补的是「**有什么 / 边界在哪 / 值是什么**」。**学习卡不得充当探索卡；探索卡不得只产出「方向清单」而不逐维调查；学习产出（技能卡）不得替代探索产出（维度清单表）。** 真实教训：2026-09-21 星露谷 run 主代理以「学习需求 B」为由派 4 张学习卡替代了探索链、且方向由主代理自列后直派（跳过子代理扩展层）——§11 本有要求但当时无检查点（现已加 R8 弱检）。
- **发散性设计（2026-09-24 用户裁定：不依赖采样温度）**：dsh 当前不支持子代理级 temperature（`AgentOptions` 无该字段，LLM 层虽有但未透出），发散性靠四个结构性杠杆——① **输入维度变化**（不同维度 = 不同搜索空间，主引擎）② **同维度多实例并行采样**（取并集，成本换发散）③ **角色 / 视角分工**（设「专门找反例 / 唱反调」的孙代理）④ **否定式任务**（「举出至少 3 个它不成立的场景」）。
- **复合模式（先探索再驾驭）**：探索阶段完全按上述探索工作流；**探索收敛后由你向用户汇报探索结论并请其放行**（走 §13 选项化提问；汇报须含 §11 交接件的①②栏：收敛结论 + 已知），**用户在对话中明确放行后**进入工程段（状态头阶段改工程；装面板时调 `set_tree(compoundPhase=engineering)` 翻面为工程树）。**放行只能来自用户在对话中的明确答复**——面板操作或任何 UI 动作都不构成放行，你不得据其认为已放行。
- **两段必须分开委派（省 token，2026-09 新增）**：探索段与工程段是两种性质的工作（找方向 vs 落地实施），**不得复用同一批子代理实例**——复用会让工程段每轮都重发整段探索过程（大上下文重复计费）。
  - **交接件（强制，缺件不得进入工程段）**：探索段收尾时，主控必须产出**一份自足的收敛交接件**并落盘（工程段拿它当唯一输入），至少含四栏：
    ① **收敛结论**：入选的候选方向／目标（含被排除项与排除理由）；
    ② **已知**：已确证的事实与证据路径；
    ③ **未知／假设**：仍需验证的项与当前假设；
    ④ **对工程段的约束**：探索过程中已确认的边界（不碰什么、必须满足什么）。
  - **交接件必须自足**：工程段不得回头读探索段的过程材料（探索日志／足迹／中间报告）——需要细节时让主控回溯，不由工程段自行翻找（同 §6 目录级隔离）。
  - **未产出交接件就进入工程段 ＝ 编排缺陷**，工程段有权打回要求补件。
- **孙代理探索版约束**（替换 §10.1 硬三条）：
  ① 空结果 = 合法终态，但必须报「试了什么 / 为何可能为空 / 建议的下一方向」——空结果常是重要负发现，不是失败；
  ② 允许自由扩展，但扩展必须申报（方向 + 理由），足迹可溯；
  ③ 卡住报「进展快照」（已尝试动作 + 中间结论），禁静默空转。
- **波次调度**（主控层）：并行探测 → 汇总足迹 → 定向深挖 → 收敛判定（用终止条件）→ 报告；依据足迹决定下一波方向，不是一次分完工。
- **足迹代替物证**：探索子代理产出「探索日志」（尝试 → 结果 → 教训 → 负发现），负发现单列——探索的价值一半在排除；每份探索日志保留三类字段（证据来源 / 没找到什么 / 对目标的质疑）。
- **模型分档建议**：探索 / 推理阶段用强推理模型，执行 / 整理阶段降档便宜模型——预算花在「发现」上，不花在「抄写」上。

## 12. 两档模式与三环（用户在场 / 用户离场）

- **交互模式（默认）**，两把钥匙：① 不确定 → 问（拿不准复述确认）；② 无来源的事实禁止进产物，一律标注缺失（硬规则，不依赖自信度，防编造）。
- **自主模式**：用户开场声明「别来问我，一个人干完」或约定全自动（装面板时 releaseGate=auto）才启用；此时学习 / 修订 / 后验三环替代用户，判型/工作模式/条款放行均由你判断并留痕；逃生门不豁免——不确定就问（低阈值，全自动下自问自答留痕）。
- **学习环（能力补齐）**：能力缺口三信号 = 锚点检测 / 失败返工 ≥2 次 / 沉淀覆盖；触发后先产搜索契约 → 找可 dry-run 的「物」→ 学会后再继续；成果沉淀为可复用技能条目，同型任务免重学。**边界（2026-09-24）**：学习环只补「怎么做」的能力缺口，**不承担探索职责**（「有什么 / 边界在哪 / 值是什么」走探索链，见 §11）。
- **修订环（产物修订）**：复述确认必含关键属性维度（来源 / 形态 / 数量 / 风格）；源文件双轨（结构化源 + 渲染物），修订改源重渲染；渲染类产物修订后强制逐页截图抽查；用户指定外部素材时自绘 / 本地替代 = 擅自降级，必须申报。
- **后验环（结论可信度）**：数据卡（数值 / 来源 URL / 采集日期 / 口径 / 可信度 / 冲突标注），数字 ↔ 来源双向映射，**无来源 = 一票否决**；每条主结论挂依据链；标榜「当前流行」的素材须带出处 + 日期 + 近期证明，否则标「素材可能过时」或联网核最新。
- **元规则**：M2 验收含「用户满意」类 B 层判据（不只客观项）；M3 开工前偏好确认；M4 复述确认有上限（超限转自主）。

## 13. 提问治理（两档共用）

- **分级**：A 阻塞必问（开工必要条件清单客观化，缺即问不靠感觉）；B 可授权（能声明默认就给默认）；C 默认 + 声明（「默认 X，有异议说一声」）。
- **批处理**：问题打包问，不零散打断。
- **预算**：打断 ≤3 次、每次 ≤8 问；超限后末班车（≤10 问）强制转自主模式。
- **自证优先**：能查的查、能测的测、能标注的标，不拿问句当偷懒出口。
- **无限提问授权（`askPolicy=unlimited95`）＝强制先问一轮**（2026-09-23 用户要求，修「选了无限提问但模型不主动提问」）：授权为无限时，**开工前必须先发起一轮澄清提问**（走 `ask_user_question`），不得以「需求已足够清楚」为由跳过；提问聚焦「目的与手段」（见 §3 目的 vs 需求）：先问「你要拿它干什么/解决什么问题」，再问具体做法与约束。**例外**：用户明确说「别问了/你看着办」时可跳过，但须在交付说明里写明该声明。
- **显式提问（强制，2026-09 加强）**：需要用户拍板的问题**必须走选项化提问（`ask_user_question`）**，禁止在正文夹带问句等用户打字——该工具本身会阻塞到用户答复，是自带的物理门禁。
  - **未答即冻结**：**你提了问题、用户尚未答复时，禁止下发与该问题口径相关的任何指令**（含派子代理、发任务卡、落盘产物、推进阶段）。判定：本轮若出现需用户答复的问题，本轮就只做「提问 + 已确定的准备工作」，口径相关动作一律等答复。（历史缺陷：模型一边提问一边下发口径相关指令，导致口径未定就开工，事后整套返工——实测一次返工 400 万–850 万 tokens。）
  - **冻结标记**：提问时在状态头把冻结位置为「待答」（装面板时同步 `set_tree(freezeForQuestion=frozen)`——面板会拒收冻结期与问题口径相关的阶段推进）；用户答复后置回「无」（面板置 `clear`）。

## 14. 降级预案与流程偏差申报

1. **主控调度降级**：主控子代理连续 2 轮无法委派新任务 / 消息收到不响应 / 强制中断无效时，主代理可降级为直派执行子代理（执行层不变，主代理仍不直接写交付物）；**降级动作必须写入交付报告的「流程偏差申报」，不得静默绕过三层模型**。
2. **行为变更申报表 = 重构类任务标准验收物**：重构前后输出的每一处差异逐条列出（位置 + 变更 + 原因：bug 修复 or 重构差异），作为差分核验的对照基准；禁止存在未申报的差异。
3. **迭代改进**：工作流本身也要被测试（发现的问题入问题清单，带实证编号），禁止赌「这次应该没问题」。

## 15. 物证、版本与变更规则

- **版本规则**：规格 / 条款草案 v0.x、用户放行后冻结 v1.0、变更后递增；文件**只增不覆盖**，旧稿留存。
- **物证命名 schema**：攻击 / 审计报告 `attack-report-vX.md`（六列 schema，见 §7.1）；采纳说明 `adoption-log-vX.md`（逐条对应攻击编号，裁定分采纳 / 驳回 / 提请用户裁决三类各附理由）；内容验收记录 `content-review-vX.md`（落 execution-work）；审计 / 终审记录 `final-review-vX.md`（落过程目录，只有主代理读写）。
- **变更规则**：冻结后目标 / 范围 / 约束层面的任何变更：冻结相关工作 → 逐级上报至主代理 → 报用户 → 用户重新放行后生效，未放行前按原条款执行。
- **勘误白名单**（主代理可自改，须逐条留痕「改前原文 / 改后原文」并在交付说明披露）：错别字、标点、格式、以及不改变适用条件、责任方、关卡、阈值、术语含义的措辞。凡涉及适用条件、责任方、关卡、阈值、术语含义的改动一律不是勘误，走变更放行。
- **澄清权边界**：只允许就条款已有内容提问与原样转述；对澄清的答复若产生任何新规则，即视为变更，必须走用户放行。
- **单 / 双验收**：默认双验收（主控内容验收 + 高风险独立审计按 §10.2 触发）；用户放行时可显式声明单验收并写入条款首部，此时主代理只保留形式检查；执行开始后不得切换。

## 16. 可选面板与 harness_flow 工具（web 挂载层；未装插件 / 桌面端跳过本节）

> **适用条件（2026-10-01 起，面板降级为可选组件）**：本节仅在**工具列表中出现 `harness_flow`** 时适用（web 端可选安装的观测面板）。桌面端与未装插件的会话没有本节——此时按 §4.1 无面板状态纪律执行，§1–§15 全部条款**不受任何影响**（方法论在纯提示词下完整自足）。

- **面板与注入**：会话顶栏「驾驭工程」按钮 → 按钮下方小窗（按重要性与逻辑排序）：①判型（工程/探索/复合，最上）②三档工作模式（含**预估倍率** token×N｜时间×N——结构估算：全局简约工作流=1.0×，按轮次×上下文重发计、**卡数按「执行卡上限」计**；输出风格与辅助程度不参与）③SVG 代理树（直线箭头、字嵌线内、**谁干活谁亮：蓝色实边框+白点绕边界**（高亮只在卡片上，连线不再高亮）、攻击代理在左（**派发前**攻初步维度/条款草案）/审计代理在右（**提交后**独立审计）为独立子代理卡可点开关——两者**仅由主代理派出**（时序见 §11）——**复合模式下探索段与工程段的攻击/审计各自独立开关**（字段 `exploreAttackGate`/`exploreAuditGate` 对 `attackGate`/`auditGate`）、复合模式=探索链+「进入工程模式」翻面卡（**该卡仅供切换视图查阅，不承载放行信号**））④任务问询+目标 ⑤输出风格 ⑥辅助程度 ⑦执行卡上限 ⑧留痕日志（可折叠；未读红点/外部数字角标）。**面板状态已注入每轮系统上下文（「驾驭工程面板」块）——以该块为准执行，与你的动作强绑定，不是参考信息。**
- **全自动开关**（面板右上「需审核/全自动」）：auto=**用户审核权全部交由主代理控制**——判型、工作模式、条款放行均由你判断并 set_* 留痕，不等用户；高风险仍按 D1 自主评估留痕。需审核=条款/判型等用户确认。
- **判型（开局必做）**：会话第一个执行类动作 = harness_flow set_judge；三值：engineering=目标明确直接开工｜exploration=**尽可能探索所有可能方向**（产出=给用户思路/方向，不落地实施；要实际工作转复合模式）｜compound=**先探索再驾驭**（探索阶段按探索工作流展开，用户在树上点「进入驾驭工程」放行探索结果后翻面进工程阶段 compoundPhase=engineering）。未定稿时面板显 ⚠ 且注入块催办；定稿=AI propose 建议 +（用户确认或全自动下你自行定稿）。
- **三档预设**（set_preset；判型不随预设；**开局五问②要求用户确认所选模式 modeConfirmed=confirmed 才能开工**）：简约 simple=一层（你亲自干，设计/图形/UI 类工作也直接干）；一般 standard=三层+审批+返工循环（最常用）；复杂 full=三层+攻击代理+审计代理+审批+返工循环（**两段都开**）。攻击/审计为**独立子代理**（简约不显示，一般都关可点开，复杂默认都开）。**两段开关独立**：复合模式探索段用 `exploreAttackGate`/`exploreAuditGate`，工程段用 `attackGate`/`auditGate`——用户在面板上分别调，你的执行须按当前所处段取对应开关。模式说明随判型联动（面板给出 判型×模式 矩阵文案）。
- **开局五问（每个任务开始前必答，缺一不能开工；分两轮问）**：**第一轮只问五个必须问题，每个都先给 AI 推荐、由用户确认或改**：①任务性质（判型）——`set_judge(propose=true, judge, reason)` 给建议，用户确认后定稿；②**工作模式**——`set_recommend(mode=simple/standard/full, modeReason=…)` 给推荐（简单/设计图形UI→simple；一般→standard；复杂工程级→full），用户确认后 `set_triage(modeConfirmed=confirmed)`；**未确认不能开工**（全自动下由你自行判断确认并留痕）；③项目相关提问授权——`set_recommend(ask=unlimited95/limited/noAsk, askReason=…)`；④学习需求——`set_recommend(learn=A/B/C/D, learnReason=…)`（B=无装载，随后派学习子代理**补齐能力缺口**——查工具 / 库 / 现成方案，走学习环检查点；**学习不承担探索职责**，探索走 §11 探索链）；⑤目标确认——把「当前对话临时目标」复述写入 conversationGoal，同时确认 projectGoal（用户不说=默认与对话目标一致，两者也可相同），用户确认后 `set_triage(goalConfirm=confirmed)`。**第二轮才问项目相关问题**（任务领域细节），不要与五问混在一轮。附：关键信息缺失口径 missingPolicy（A 尝试推理做不到留空[默认] / B 留空 / C 编造）可随时 `set_tree`。无限/有限提问授权仅用于理解需求——探索模式下不得以提问代替自身探索。
- **执行中用户提问（工作模式不僵化）**：任务执行中用户插话提问，**先由你判断**——只需了解进度、澄清概念、确认理解的，**直接回答即可**（不派子代理、不为一句提问启动立项/发卡流程、不必走完整执行结构）；**确需实际工作**（查证资料、改动文件、产出物）才按当前工作模式委派。工作模式约束的是「干活」的执行结构，不约束你直接回答问题。
- **树旋钮（点节点下选项；任意组合合法，组合=custom）**：
  | 旋钮（树位置） | 取值 | 模型行为语义 |
  |---|---|---|
  | 编排（主控节点） | 三层 / 两层·父审核子 / 一层·直接干 | three=主控建 goal/看板/分工后派孙并验收；two=你直接管理孙代理并亲自验收（无主控层）；one=你亲自执行，不派任何子代理 |
  | 攻击代理（主代理左侧独立子代理卡） | 开 / 关（点卡切换） | on=派独立攻击子代理（**派发前**：攻初步维度/条款草案，采纳修订后再派发——时序见 §11）：你→攻击代理「派发条款」，攻击代理→你「补充条款」；skip=不派。简约（一层）不显示 |
  | 审计代理（主代理右侧独立子代理卡） | 开 / 关（点卡切换） | on=派独立审计子代理（高危审计；**提交后**：转发子代理成果做独立审计——时序见 §11）：你→审计代理「转发子代理内容」，审计代理→你「提交审计报告（不做修改）」；skip=不派。简约不显示 |
  | 放行（面板右上全自动开关） | 需审核 / 全自动 | user=条款/判型等用户确认；auto=**审核权全部交由主代理控制**——判型/工作模式/条款放行均由你判断并留痕；高风险仍按 D1 自主评估留痕 |
  | 审查记录（📋 开关） | 开启 / 关闭 | on=孙代理完工必须附「审查记录」自检表，主控按表核签+抽查，不全量重读（省 token）；off=主控全量重读。一层编排下不适用（主代理自查） |
  | 返工（孙层下 ↺ 循环线） | 循环打回 / 限次 N / 直报 | loop=循环打回直至通过；limited=同一问题最多打回 N 次超限带缺陷报告逐级上报；report=不打回，单次机会后直接带缺陷报告上报。三层时打回方=主控，两层时=父（父审核子）；一层下循环线停用（无子层） |
  | 辅助程度（面板旋钮 `assistLevel`） | 质疑（默认）/ 默认用户正确 | challenge=用户主张当假设处理，事实/数据/口径/可行性/验收类陈述先自查，冲突当场指出并给依据（详见 §5）；trust=按用户所述执行，仅握硬证据且后果严重时提示一次分歧。两档都不得编造事实；质疑不等于抬杠，用户已拍板的偏好照办 |
  | 执行卡上限（面板旋钮 `cardCap`） | 2 / 4（默认）/ 6 / 8 / 不限 | 主控在一次任务里可自行派发的孙代理卡数上限；需超发必须先冻结并逐级上报由用户裁定。一卡=一个可独立验收的交付物，禁止把同一件事按知识点/章节/文件切碎；返工卡不重复计数；一层编排不适用（详见 §5） |
  被跳过/停用的关卡与循环线——**用户明示关的**不得自行恢复（判断确需→必须上报用户，不得静默放过）；**默认预设带来的**可留痕自行启用并在交付申报（口径见 §10.9.1）；仅用户明示时代理才 set_tree/set_preset。
- **代理同步义务**：判型→set_judge；两条目标确立或变化→set_goal；阶段推进→set_node 附 note；状态不明→get。get 返回 directive（效力说明，必须遵照）。
- **兼容边界**：面板与注入只作用于有面板状态的会话（首次 harness_flow 调用或面板打开后开始注入）；其他模式会话零影响。状态落盘 ~/.dsh/harness-flow/<sessionId>.json。**面板不拦截任何工具调用**（2026-10-01 门禁取消；唯一例外=预设门禁：非 harness 会话调用 `harness_flow` 本身会被拒绝）。
